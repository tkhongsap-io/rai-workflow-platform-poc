# Evaluation set `qc-eval-synthetic@1`

The synthetic set the W4b content QC is measured on ([W4b plan](../../../../docs/engineering/implementation-plan-w4b.md) section 11.1; [evaluation plan](../../../../docs/evaluation/plan.md)). This directory holds the **dev split** (W4-09a). The held-out split, its renderings, the freeze and `disagreements.md` come with W4-09b; the harness that runs the set is W4-08a.

Everything here is invented inside this repository. No case, document, sentence, name or identifier is copied from a real review case or from any real document. `provenance.test.ts` greps every file here and every generated byte (also inside compressed streams) against the `slice1-synthetic` denylist on each run.

## Files

| File                 | Content                                                                                                                                                                                   |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `types.ts`           | case, document, claim and label types; locators follow the W4-16 contract (ordinals and A1 references, never text)                                                                        |
| `vocabulary.ts`      | the dev rendering of the claim grammar: key order, separators, answer words, questions, item keywords, metrics, sheet names                                                               |
| `cases.ts`           | the case rows: template, model type, stage, vendor flag, the nine slot states, and each document's pages of text lines and claims                                                         |
| `render.ts`          | document renderers over `../generate/{pdf,ooxml,png}.ts` (Node built-ins only), returning each claim's locator                                                                            |
| `labels/<case>.json` | the expected runs: every upload of an attached slot 1, 2 or 5, the submit, and one approve attempt per lane; both run parts (`deterministic`, `content`) with status, reason and findings |
| `labels.ts`          | reads the label files                                                                                                                                                                     |
| `generate.ts`        | `npm run fixtures:eval:generate`                                                                                                                                                          |
| `manifest.json`      | `{ name, version, sha256, split, documents }`: the set identity and each document's digest, size, case, slot, format and media type                                                       |

## Generating the documents

```bash
cd rai-web
npm run fixtures:eval:generate                        # checks manifest.json, writes .local/eval-fixtures/qc-eval-synthetic@1/
npm run fixtures:eval:generate -- --write-manifest    # after changing a case, a label or a renderer
npm run fixtures:eval:generate -- --out /some/dir     # another output root
```

Documents land at `.local/eval-fixtures/qc-eval-synthetic@1/<split>/<case>/slot-<n>/<filename>` (gitignored), with a copy of the manifest. No document byte is committed. The same inputs always give the same bytes: FlateDecode PDF streams and deflated ZIP parts come from the fixed-Huffman encoder in `../generate/deflate.ts`, not from the platform's zlib. Every document passes the upload sniff as its media type, so it can also be uploaded through the UI.

## Identity

The printed identity is `qc-eval-synthetic@1 <sha256[0:12]>`. The hash covers every file in this directory except `manifest.json` and tests, followed by the sorted document digests, so a changed case row, label, vocabulary or renderer changes it. Until W4-09b freezes the set, a change refreshes the manifest in the same PR; after the freeze, a change needs a new version (`@2`), never an edit of `@1` (decision 14).

## Labels

Written by the agent team and marked `labelledBy: "agent-team, provisional (Ta delegation 2026-09-27); lane-expert sign-off pending (D09)"`. The lane experts and the AI/COE lead sign when D09 names them (decision 14b). Labels follow the plan's reading rules: on an approve attempt a content rule reads only the run lane's slots (decision 28), so a DPO or IT/Security attempt carries no slot-1 content label, and an unreadable slot 1 makes only the AI/COE content part unavailable; an extraction outage makes only the content part unavailable, and the metadata part keeps its findings (decision 27). A label is never changed to fit a runner's output: a disagreement is recorded (W4-09b).

The dev documents use one rendering of the synthetic claim grammar (`vocabulary.ts`): English keys in a fixed order, `key: value` pairs joined by `; `, English or Thai answer words, hallucination values in percent. The rule label lists in the catalogue `params` (W4-06a-d) are expected to cover it.
