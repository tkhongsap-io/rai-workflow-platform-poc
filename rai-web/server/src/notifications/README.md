# Case notifications (W3-03a)

`createNotifications({ db, sink, identities, publicBaseUrl, emitter })` consumes the existing W2 outbox. Pass a database pool handle, never a workflow transaction. `deliverInitial(notificationId)` returns a receipt or `undefined` when the row is absent, already attempted, or outside the three case-event kinds. `deliverPending(correlationId?)` handles unattempted queued case rows, optionally restricted to the committing request's correlation ID.

`app.ts` registers the post-response hook before routes, and a startup backlog pass. `start.ts` binds the configured W1-11 sink only in fixture identity mode; local-google and production do not receive a synthetic recipient directory or mail delivery. Both memory and file modes stay local. Shutdown waits for active hooks before closing the database. There is no mail HTTP endpoint or polling loop.

The worker locks a notification row in its own transaction, reads its committed audit/version/decision, and applies the existing `case.view` policy plus event-specific recipient selection. Lane-open includes all lane holders, including self-excluded decision makers who may still view; send-back and Ready include only the owner. Unknown, out-of-scope and non-synthetic addresses fail closed. Latest stored session locale wins, otherwise identity preference or Thai. The case name and recorded defect count are read at initial composition; the version link, deciding feedback, frozen SLA/calendar and audit identity come from the referenced version/event. Templates never receive document bytes or finding evidence.

Success (including a sink duplicate) writes `status=sent`, `attempts=1`, null next-attempt/error. Failure writes `status=queued`, `attempts=1`, null next-attempt, and a safe error code. Only the four permitted delivery columns change. W3-04 owns scheduling, attempts 2–4 and terminal failure. The initial selector never retries. A rolled-back event cannot be read on this pool; a failure cannot undo its business transaction. Cross-worker row locking plus the W1-11 sink key cover concurrent calls and sink success followed by a database commit failure (file sink persists keys across restart; memory is process-local).

`mail.enqueued` is emitted once on the first validated committed-row attempt, then `mail.sent` or `mail.attempt_failed`, using the outbox correlation ID. Fields follow the existing W0-10 catalogue; no address, dedup key, body or URL enters logs. Infrastructure scan failure uses `error.captured`; it does not turn a successful business response into an error.

W3-03b owns digest provenance/job rows and daily scheduling. Digest notifications are explicitly excluded here. W3-07 owns operator views and migrations. This module introduces no migration, authorization action or new shared mail type. Its additive locale-key prerequisite is separate from the consumer commit.

## W3-04 handoff

`loadCommittedCaseRequest(tx, row, { identities, publicBaseUrl })` is the reusable, read-only composition entry point. The caller must obtain the row on its own dispatcher transaction, after the business transaction commits; never pass a workflow transaction. It returns DeliveryRequest with initial attempt 1; the dispatcher sets the actual attempt before delivery. It performs audit/version/decision checks, recipient revalidation, locale lookup and rendering, with no status writes or logs. `NotificationRow` is the existing Drizzle row type, exported for this seam.

No historical failure-completion timestamp is stored by W3-03a. Initial failed rows have `attempts=1`, `status=queued`, `next_attempt_at=NULL`. W3-04 must conservatively schedule their first retry from recovery time, not infer failure time from `created_at`. Crash accounting remains the parent's W3-04 contract decision. W3-04 replaces createNotifications/registerNotifications' initial runner with one dispatcher using this loader; do not register both runners. No leases, migrations, or backoff policy are introduced here.
