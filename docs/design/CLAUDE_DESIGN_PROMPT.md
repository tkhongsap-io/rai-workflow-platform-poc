# True Corp RAI review desk: interactive design brief

Create a polished interactive desktop-first web-app design artifact, titled “True RAI Review Desk”, for developer handoff and a team walkthrough. This is a synthetic prototype only, not production application code. Build a complete clickable journey with working state changes, not screenshots or disconnected dashboards. Do not deploy, connect services, send real email, or use real customer/employee data.

BRAND: True Red #E00000 for primary actions and selected states; ink #303C46; blue #007AD0 for secondary information; backgrounds white/#F9F9FC/#F3F3F6; border #E2E8F0; muted #64748B. Segoe UI, Arial, Helvetica Neue, sans-serif. BetterTogether is proprietary and unavailable; do not download or assume it. No fabricated True logo: use a clean “True Corp” textual identity unless an authentic supplied asset exists. Working palette from True website, not formal brand certification. Premium enterprise design: generous breathing room, precise alignment, readable 14-16px body, restrained red, no decorative gradients or card nesting. Case cards for queue and three equal parallel lane cards in case detail; documents and history as clean rows. Responsive desktop 1440, tablet 834, mobile 390. Accessible labels, visible focus, text+color statuses, keyboard-operable dialogs. English UI, Thai names need not be used.

SCOPE: This app is a review desk, NOT official AI register, NOT eight-stage lifecycle. External reference source_record_id is known ID or Unknown; no dual-write. Ready for launch means review-desk completion only; Council/ITSM remain outside. Show Prototype / synthetic data. Add a clearly separate Demo controls strip with six-role switcher, reset demo, scenario selection and design notes; this is not production login or authorization.

ROLES: owner sees own cases; BU SPOC sees BU cases; AI/COE, DPO, IT/Security see all but act only own lane; Admin manages configuration, not implicit lane approval. Use at least two synthetic cases with different owners/BUs to demonstrate scoped views. No backend security claim. Notification preview only, not send.

SCREENS/JOURNEY:
1 Review queue: search/filter status, owner, group, external reference; case cards show case name, owner/BU, version, state, all 3 lane statuses, findings count and next action. Owner New case creates a real in-memory draft via validated form. Include meaningful no-match and empty states.
2 Case overview and draft pack: nine slots: risk screening, privacy checklist, DPA, SOW, BRD, architecture, security assessment, RAI deployment checklist, supporting docs. Four slot dispositions attached, not yet, missing, N/A with mandatory reason. Non-vendor DPA/SOW default N/A with reason. Use Add sample document rather than pretending real file storage. Show document detail preview with synthetic evidence. Working save draft, cancel and submit. Freeze submitted version; never edit past submitted snapshots.
3 Submission runs simulated QC and always permits submit with quality findings. All 3 lanes open in parallel: AI/COE slots 1+5 provisionally; DPO 2+3+4+5; IT/Security 5+6+7+8; supporting docs not gate. Show mapping ambiguity 5 vs7 in design notes only, not as settled policy.
4 Reviewer workspace: current case/version always visible, parallel lane cards, findings BEFORE actions; evidence links open real sample evidence panel. Approve attempt runs simulated lane QC and exposes findings, but quality findings never disable lane approval. Send back requires an artifact and specific feedback. Show toast and audit event for successful changes; no dead controls.
5 Send-back preserves immutable v1, opens one successor v2 draft. Owner sees actionable feedback, edits and resubmits. For demo use full three-lane re-review, labelled proposed pending stakeholder decision. Stale version approvals cannot modify the latest case. History allows viewing v1 read-only with its original documents/decisions/findings.
6 Completion: three CURRENT-version approvals AND no undispositioned findings. Distinguish “All lanes approved · awaiting disposition” from “Ready for launch”. Findings can be fixed with evidence, waived with reason, or N/A with reason. For demo only designate lane reviewers to disposition their lane's findings; label this provisional authority in design notes. Do not permit Admin or owner to implicitly waive reviewers' findings. All prior events preserved. Completion disclaimer “Review desk complete. Council and ITSM authorization remain outside this desk.”
7 Admin: editable template version, QC thresholds and SLA, role mapping preview; publish a new config revision without reload. Existing versions retain original config; next submission uses new revision. Mapping is a demo, not live AD. Proposed DPO SLA 3 working days, other lanes 5; no automatic escalation; due dates illustrative until holiday/timezone policy confirmed.
8 Notifications panel: lane-open, send-back, readiness, SLA-breach synthetic previews with case deep links; no emails sent. Risk proposal: show synthetic answers/evidence and proposed tier, Unknown if incomplete; High shows Council confirms and never skips lanes. Actual seven-question instrument unconfirmed, so no fabricated official questionnaire/scoring; use explicitly labelled demo scenario selection.

QC: three triggers upload, submit, approve. Completeness, contradictory evidence and missing hallucination metric/denominator/threshold. Extraction accuracy is NOT hallucination rate. Exact v1.0 Sheet3 SL2.1 bands H<1%, M<2%, L<3%, not inherited by v2.0. Classic ML uses relevant metric or N/A. Simulated QC unavailable -> explicit finding, never clean pass. Include seeded v1.0 mismatch case, v2.0 case and unavailable scenario. Ground findings in sample document references. Show simulated checks label, not a real AI evaluation score.

DEMO SCENARIOS: one complete owner->submit with defects->reviewer send-back->owner v2 resubmit->three approvals->disposition->ready flow; a separate all-lanes-approved-with-open-finding state for testing final gate; v2.0 template-isolation and QC-unavailable scenarios. Reset returns to deterministic seed. Persistence only local if needed, with clear reset; no network calls required.

HANDOFF: include a Design notes/help panel with screen inventory, component/tokens, role/action matrix, state transitions, mocked-vs-real distinctions, responsive behavior, assumptions and developer checklist. Make every visible control functional or visibly disabled with explanation. No fake working upload, auth, email, risk engine or AI service. After creation, inspect your own design for state inconsistencies, clipped content, unreadable controls, missing buttons and keyboard issues and fix them. Report what you actually tested, not blanket bug-free claims. Prefer one coherent artifact we can iterate, not unrelated variants.
