## 0. Scope and non-goals

W7 in [BUILD_PLAN](../../BUILD_PLAN.md) is operator rehearsal and PoC acceptance. Its real form, operator Nakhun running 3-5 **permitted** cases with real reviewers, needs D08 real-data permission and retention and real people. That stays **pending and is not claimed** by anything below. This plan builds every part agents can build and prove on synthetic data:

1. **W7-00 restore and rollback.** A backup command, a restore command into a fresh database and blob directory, a restore verifier (A07 re-proved on the restored copy), a migration rollback classification with a rollback check, runbooks, and a recorded synthetic rehearsal of backup, restore and an operator-procedure rollback of one deployment.
2. **`network` identity mode, source `allow-list`** (W0-03 section 4.2; AD is W8). A non-loopback bind is allowed only in `network` (and in `production`, which cannot start before W8 without Entra), `network` refuses a non-`https` `PUBLIC_BASE_URL` (the recorded 2026-09-24 deferral), and the A01 network clause is tested. This is what lets the single deployable later run on a host such as Replit.
3. **The directories `network` mode needs to be usable end to end:** a persisted subject profile, a mail recipient directory and a business-unit directory that do not come from the fixture package, and an in-product mail file drop (no transport).
4. **A rehearsal kit:** a synthetic rehearsal case set and its loader, timing capture, and templates for the deficiency log, timing sheet and acceptance report.
5. **An agent-run synthetic dress rehearsal** that follows the W6 operator guide end to end on the real server, a scripted twin of it, recorded findings, and fixes for blocking defects (W7-15.n).
6. **A deployment-readiness note** for running the one deployable on a generic Node + Postgres host. No deploy is performed.

Non-goals:
- W8, production identity (Entra, `production` mode start), True host, D10 values, release runbooks for True.
- Any external network call from the product or tests: no model provider, no SMTP, no object store, no real IdP. OIDC in tests goes through the existing `discovery` and `exchange` seams (`identity/adapter.ts` `CreateIdentityAdapterInput`).
- A non-loopback bind by any agent, test or CI job (decision W7-D2).
- Real data, real mail, real accounts, operator acceptance. A developer or agent demonstration never substitutes for operator acceptance (BUILD_PLAN W7 exit).
- Admin editing (W6), risk scoring (W5), content QC (W4b). W7 consumes what those packages merged; it does not change their rules.

## 3. W7-00: backup, restore, rollback

### 3.1 Backup (W7-01)

`npm run backup [-- --label <text>]` → `server/src/operator/backup.ts` (`runBackup(config, tools, now)`), tools resolved by `server/src/operator/pg-tools.ts` (`resolvePgTools(value)` → `{ dump(args, out), restore(args, in), version() }`).

1. Refuse unless `pg_dump`'s major version equals the server's (`SHOW server_version_num`), reason `pg_tools_version_mismatch`.
2. `pg_dump --format=custom --no-owner --exclude-table-data=session` as `rai_owner` (`DATABASE_MIGRATE_URL`) to `<BACKUP_DIR>/<id>/db.dump`, where `<id>` is `YYYYMMDDTHHMMSSZ-<label>`. Session rows are excluded so that a restore can never revive a revoked session and a backup holds no token hashes; restored users sign in again.
3. After the dump finishes, copy every blob referenced by `artifact` (`bytes_state = 'present'`) from `BLOB_DIR` into `<id>/blobs/` in the W0-04 layout (`sha256/<h[0:2]>/<h[2:4]>/<h>`), verifying each hash while copying.
4. Write `<id>/manifest.json`: `{ backupId, createdAt, buildCommit, journal: [{tag, hash}], dumpSha256, blobs: { count, totalBytes }, tableCounts, frozenDigest, fixtureSet }`. `frozenDigest` comes from `server/src/operator/frozen-digest.ts` `frozenDigest(exec)`: SHA-256 over the canonical JSON of the ordered rows of the tables W0-04 forbids migrations to rewrite (submitted `pack_version`, frozen `artifact_slot`, `artifact`, `lane_decision`, `qc_run`, `qc_finding`, `disposition_event`, `audit_event`, published `configuration_revision`). The same function serves the W0-04 migration test.
5. Directory 0700, files 0600. No URL, password or row content is printed.

### 3.2 Restore and verify (W7-02)

`npm run restore -- --from <backupDir> --target-db <name> --blob-dir <dir>` → `server/src/operator/restore.ts`:
- Refuses when the target database or blob directory exists (`restore_target_exists`), when `dumpSha256` does not match, or when the target name equals the live database's.
- As `DATABASE_ADMIN_URL`: `CREATE DATABASE <name> OWNER rai_owner`, then the per-database statements of `docker/postgres/init/001-roles.sql` that are not in a dump (`REVOKE CREATE ON SCHEMA public FROM PUBLIC; GRANT USAGE ON SCHEMA public TO rai_app, rai_operator`), then `pg_restore --no-owner --role=rai_owner --exit-on-error`. Triggers are in the dump's post-data section, so they are created after the data load and fire on nothing during it.
- Copies `<backupDir>/blobs/` into `--blob-dir`.

`npm run restore:verify -- --from <backupDir> --target-db <name> --blob-dir <dir>` → `server/src/operator/restore-verify.ts` (`verifyRestore(...)` → `{ ok, checks: Array<{ id, ok, detail? }> }`). It connects with `DATABASE_ADMIN_URL` with the database name replaced by `<name>`, and runs each role-specific check inside its own transaction after `SET LOCAL ROLE rai_app` or `SET LOCAL ROLE rai_owner` (the admin role can assume both; `rai_owner` cannot assume `rai_app`, so a single owner URL would not do). It is read-only except the negative probes, and every transaction is rolled back:

| Check id | Proves |
|---|---|
| `journal` | `drizzle.__drizzle_migrations` hashes equal the manifest's journal |
| `counts` | per-table row counts equal `tableCounts` (session excluded) |
| `frozen_digest` | `frozenDigest` of the restored database equals the manifest's |
| `manifest_hashes` | for every submitted `pack_version`, `manifestHash` (`versions/manifest.ts`) recomputed from its `artifact_slot` rows equals the stored `manifest_hash` |
| `blobs` | `verifyStore` (`operator/store-verify.ts`) on the restored blob directory: all referenced objects present, hash and size match |
| `a07_frozen_slot` | as `rai_app`, `UPDATE artifact_slot` on a submitted version fails with `rai.frozen_version` |
| `a11_audit` | `UPDATE` and `DELETE` on `audit_event` fail as `rai_app` (privilege) and as `rai_owner` (trigger) |
| `grants` | the set of tables on which `rai_app` holds `DELETE` (`information_schema.role_table_grants`) is a subset of the named exception list `{configuration_draft}`: the W0-04 roles rule as amended by W6-02 ("no `DELETE` on any table except `configuration_draft`", an Admin working copy that is not evidence; [W6 plan](implementation-plan-w6.md) section 3). Before W6-02 merges the set is empty, which also passes, so the check holds in either merge order. Any other table with a `DELETE` grant fails and is named in `detail` |

Exit 0 only when every check passes. The W7-02 integration test then spawns the real server (`tests/support/process.ts` `startTestServer`) against the restored database and blob directory and reads, over HTTP as fixture users, a sent-back case's version 1 and version 2, their findings and decisions, and downloads one artifact, comparing its SHA-256 with the manifest. The server's `DATABASE_URL`/`DATABASE_MIGRATE_URL` for that run are the configured role URLs with the database name replaced. In its `after` hook the test stops the server and drops every `rai_restore_*` database it created (`DROP DATABASE ... WITH (FORCE)` as admin) and removes its blob directories, so reruns start clean.

### 3.3 Migration classes and rollback check (W7-03)

- **Class map:** `server/src/db/migration-classes.ts` exports `MIGRATION_CLASSES: Record<tag, 'additive' | 'restore-required' | 'copy-forward'>` with the W7-D9 values. A unit test fails when a file in `server/drizzle/` has no entry, or when a migration numbered after W7-03's lacks a header `-- rollback expectation: <class>;` equal to its entry. Only the three W0-04 values are accepted in a header after W7-03; a migration of another package merged before W7-03 keeps whatever header it has and gets its class from the map (as 0007 and 0009 do). The W5 plan's draft header `rollback expectation: forward repair only` must become one of the three values if W5-03 merges after W7-03 (section 14).
- **Migration** `server/drizzle/00NN_w7_03_migration_class.sql` (number assigned at rebase, section 9): `CREATE TABLE schema_migration_class (hash text PRIMARY KEY, tag text NOT NULL UNIQUE, rollback_class text NOT NULL CHECK (rollback_class IN ('additive','restore-required','copy-forward')), recorded_at timestamptz NOT NULL DEFAULT now())`; `GRANT SELECT` to `rai_app` and `rai_operator`; an UPDATE/DELETE guard trigger like the other append-only tables, whose function is named `rai_schema_migration_class_guard()` (the `rai_` prefix lets `w1-00-migrations.test.ts` `dropEverything` remove it on rerun). Header: `rollback expectation: additive`.
- **Schema test:** `tests/integration/w1-00-migrations.test.ts` deep-equals the full lists of public tables, triggers and `rai_app`/`rai_operator` grants, so W7-03 adds `schema_migration_class`, its guard trigger and its two `SELECT` grants to those lists (W7-06 does the same for `subject_profile`).
- **Writer:** `db/migrate.ts` `runMigrations`, after the apply loop, calls a new `recordMigrationClasses(client, folder, migrations)`. It is **conditional**: it first runs `SELECT to_regclass('public.schema_migration_class')`, and when that is `NULL` (a folder or database that does not yet hold the W7-03 migration) it does nothing and returns. This keeps every historical-folder caller green, in particular `tests/integration/w3-07a-migration-contract.test.ts`, which calls `runMigrations(ownerUrl, scratch)` on a scratch folder holding only 0000-0006 and must keep passing unchanged. When the table exists it maps each hash to its tag by reading `<folder>/meta/_journal.json` (`readMigrationFiles` returns `hash`, `folderMillis` and `sql`, no tag; entries are paired by index, and a count mismatch between journal and files fails with `migration_journal_mismatch`), then inserts one row for every hash recorded in `drizzle.__drizzle_migrations` that the folder's journal names (already-applied ones included, so the first run after W7-03 back-fills 0000 onward) with its `MIGRATION_CLASSES` class (`ON CONFLICT (hash) DO NOTHING`), and fails with `migration_class_changed` if a stored class differs from the map. A tag with no map entry fails with `migration_class_missing` (the unit class-map test catches this first). Unit tests pin the journal pairing; integration tests pin the no-table skip and the rerun idempotence.
- **Readiness:** `observability/probes.ts` `migrationStatus(expected, applied, classOf)` returns `ahead` when `expected` is a strict prefix of `applied` and every extra hash has class `additive`; otherwise the existing `unknown`. `classOf` reads `schema_migration_class` (by hash) from the database, never the in-code map: an older binary's `MIGRATION_CLASSES` does not know the newer tags, and only the newer build's `migrate` run recorded their classes. A hash with no row counts as not additive (`unknown`). Binary-only rollback is therefore possible only to a build at or after W7-03; an older binary has no `ahead` state and needs the restore path. `ReadinessReportSchema.store.migrations` (`shared/src/schemas/observability.ts`) gains `ahead`, and because `web/src/i18n/operator-labels.ts` maps every `OperatorValue` with `satisfies Record<OperatorValue, LocaleKey>`, W7-03 adds `ahead: 'operator.value.ahead'` with th and en keys (consolidated 2026-09-27; without it the typecheck fails); in `computeReadiness` (`observability/health.ts`) the `bounded()` allowed list for the migrations probe gains `'ahead'` (otherwise the value is coerced to `unknown`), and the ready condition becomes `migrations === 'current' || migrations === 'ahead'`. The business-route gate in `app.ts` blocks only on `pending`, so it serves `ahead` without change. This implements W0-04's "if ahead by an additive migration, it serves", which the code does not do today (`migrationStatus` answers `unknown` for any extra row).
- **Rollback check:** `npm run release:check-rollback -- --target-migrations <path to the target release's server/drizzle>` → `server/src/operator/rollback-check.ts` prints one verdict: `binary_only` (target journal is a prefix, extras all additive), `restore_required` (names the first non-additive extra tag and lists the backups in `BACKUP_DIR` whose manifest journal equals the target's), or `incompatible` (target journal is not a prefix). Exit 0, 3 and 4 respectively.

### 5.3 Directories and mail file drop (W7-07)

- `server/src/notifications/file-drop.ts` `createFileDropMailSink({ dir, publicBaseUrl, now })` implements `MailSink` (`shared/src/mail/types.ts`, identity `{ sink: 'file', version: 'w7-07' }`) plus `health()`. `DeliveryRequest` carries no notification id (only `dedupKey`, `event`, `recipient`, `deepLinks`, `digestCases`, `mail`, `attempt`), so files are named exactly as the fixture `FileMailSink` names them: `<mailFileStem(dedupKey, attempt)>.json` (`{ request, receipt }`, `receipt.sinkMessageId` = the JSON file name) plus `<stem>.txt` (rendered headers and body, with `X-RAI-Sink: file (in-product drop; nothing was sent)`), where `mailFileStem` = `sha256(dedupKey).hex[0:16]-<attempt>` so no address becomes a file name. Behaviour, matching `fixtures/src/substitutes/mail-sink/base.ts` and `file.ts` step for step:
  1. **Validate** with `validateDeliveryRequest(request, origin)` (`origin` from `publicBaseUrl`); a failure answers `failed` with its code and writes nothing.
  2. **Ready:** on first use (and again after a failed load) create the directory (0700) and **rebuild the accepted-key index** from every `^[0-9a-f]{16}-\d+\.json$` file whose receipt is `delivered`; a half-written or foreign file marks nothing accepted. A load failure answers `failed` / `sink_failure`.
  3. **Duplicate:** a `dedupKey` already in the index answers `duplicate` (`error.code 'duplicate'`) and writes nothing. `notifications/service.ts` depends on this receipt (it logs `mail.deduplicated`), and the restart rebuild keeps it true across a process restart.
  4. **Record:** write the `.txt`, then the `.json`, each to `<name>.<pid>.tmp` (flag `wx`, mode 0600) and `rename`; then add the key to the index and answer `delivered`. A write failure answers `failed` / `sink_failure` and leaves the key unaccepted.
  5. Concurrent deliveries of one `dedupKey` are serialized per key, as in `base.ts`, so two attempts give one `delivered` and one `duplicate`.
  There is no forced-failure control (that is a test substitute feature). `no-external-mail.test.ts` (fixtures) gains `server/src/notifications/file-drop.ts` in the files its transport-import rule walks.
