# Review: extraction worker host, protocol and limits (W4-05b, #212)

Framed in [intent](intent.md), [spec](spec.md) and [plan](plan.md). Source: the W4-05b row of section 15 of the [W4b plan](../../docs/engineering/implementation-plan-w4b.md), sections 4.2 and 4.4, decisions 5 and 23, and the provisional [ADR-0006](../../adr/0006-qc-engine-and-extraction.md) (the plan wins over issue #212). Decisions implemented: register rows "Ta's delegation (2026-09-27)" and "W4b delegated rulings (provisional)"; parser isolation is WA-D08 (decision 5), and D08 stays open for the DPO and IT/Security. Synthetic data only; no network call, no model, no deploy.

## Change

All new files under `rai-web/server/src/qc/extraction/`; no existing file changed in `rai-web/`.

- **Port** (`port.ts`): `Locator` (the shared `EvidenceLocator`), `Segment`, `ExtractResult`, `Extractor` as the plan's section 4.2 block, plus `EXTRACT_FAILURE_REASONS`.
- **Limits** (`limits.ts`): `ExtractionLimits` (`timeoutMs` 500-9000, `maxMemoryMb` 64-512, `maxTextChars` 1000-2 000 000, `maxConcurrency` 1-4, `maxInputBytes` at least 1) with `EXTRACTION_LIMIT_BOUNDS` exported for W4-13b's config refusals; `FIXED_WORKER_LIMITS` (50 000 segments, 20 MiB per part, 100 MiB per artifact, 2 000 PDF pages, 100 000 PDF objects); `extractionLimitsProblems`; `workerLimitsOf`.
- **Protocol** (`protocol.ts`): `buildWorkerRequest` (`{ mediaType, bytes, limits }`) and `classifyReply`, which counts the output caps first (`limit_output`) and then checks the reply against a TypeBox schema with no extra keys (the shared `EvidenceLocatorSchema` for locators; only `unreadable`, `limit_bytes` and `limit_output` may come from a worker); anything else is `crash`. The version is the host's.
- **Host** (`client.ts`): `createWorkerExtractor(limits, { entry?, onFork? })`. One `fork` per call with `env: {}`, `serialization: 'advanced'`, `stdio: ['ignore', 'ignore', 'ignore', 'ipc']`, the parent's loader flags only for a TypeScript entry, `--max-old-space-size`, and the permission model for a JavaScript entry. Byte cap → `limit_bytes` before any fork; aborted signal → `limit_time` before any fork; wall clock from fork or abort → SIGKILL, `limit_time`; over-cap reply → `limit_output`; SIGABRT or exit 134 → `limit_memory`; any other exit before a reply, a spawn or send error, or a malformed reply → `crash`. The worker is SIGKILLed once its reply is read. A FIFO semaphore counts live processes (a slot frees on `exit`); a queued call that aborts never forks. `version` is `rai-extract/1+<server version>`. `selfTest()` is true when a worker round-trips a probe with a well-formed reply. No logger, no state between calls.
- **Worker** (`worker/extract.ts`, `worker/main.ts`): one message in, one reply out. An empty format registry keyed by media type (W4-05c and W4-05d register DOCX, XLSX and PDF), a `SegmentSink` that enforces the text and segment caps, and a typed `ExtractionStop` for `unreadable`, `limit_bytes` and `limit_output`; any other throw kills the worker (`crash`). No segment is `unreadable`.
- **Tests** (48 new unit tests; 43 in the first push, 5 added in round 1): `limits.test.ts` (6), `protocol.test.ts` (11), `worker/extract.test.ts` (8), `worker/module-graph.test.ts` (2), `client.test.ts` (19), `latency.test.ts` (2). Fault workers for the host limits are plain ES modules in `test-workers/` (hang, heap, crash, silent exit, malformed reply, extra key, flood, echo, slow, permission probe), reached only through the `entry` option, so the product worker has no test hook.

## Fork latency (plan section 4.2)

Worst W4b case: an approve attempt that reads slots 1 and 5, two extractions at concurrency 2, fork to reply, against `QC_EXTRACT_TIMEOUT_MS=4000` per extraction and half of the 10 000 ms deadline for the pair.

| Layout                                                                           | Where measured                                                                    | Two-slot attempt | Limit                     |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------- | ------------------------- |
| Source (`tsx` loader)                                                            | `latency.test.ts` in `npm run test:unit` (runs in CI's unit job), four local runs | 42-52 ms         | < 5000 ms; each < 4000 ms |
| Precompiled JavaScript (worker transpiled by TypeScript in the test)             | `latency.test.ts`, same runs                                                      | 21-26 ms         | same                      |
| Built (`npm run build` output, `server/dist`, plain `node`, permission model on) | a scratch script importing `server/dist/qc/extraction/client.js`, five attempts   | 23-25 ms         | same                      |

The source layout leaves far more than half of the deadline, so the precompiled-entry fallback is **not** taken: the source layout keeps forking `worker/main.ts` through `tsx`. The unit test asserts the limits on every run, so CI would fail if a runner's latency ever came near them; the CI numbers are printed as `fork latency (...)` test diagnostics in the unit job's log. The local numbers were taken while other lanes ran suites on the same machine, with a warm `tsx` cache.

## Deviations

Choices made under Ta's delegation of 2026-09-27 where the plan is silent or does not fit; each keeps the plan's contracts.

- **Permission flags on the built layout only.** The plan adds Node's `--permission` "if W4-05b shows they work under both the source (`tsx`) and built layouts; otherwise W4-05b records why not". Result: they work under the built layout and not under the source layout. Under `tsx`, the worker is transformed by esbuild, which starts a worker thread and a service process, and the permission model refuses both (`ERR_ACCESS_DENIED`, `WorkerThreads`); making it work would need `--allow-worker --allow-child-process --allow-fs-read=*`, which allows exactly what the model is for. Under the built layout, `--permission` with reads limited to the worker's own directory and the ancestor `package.json` files works (measured above; the path is resolved with `realpath`, because the model matches real paths). The choice: a JavaScript entry (production, and every precompiled or `.mjs` entry) forks under the permission model, which denies file writes, child processes, worker threads, native addons and WASI; the TypeScript source entry (tests and local development only) forks without it. This is stricter than "record why not" and never weaker than it. A test (`permission-probe.mjs`) shows the worker cannot write a file or start a process. The module-graph test stays the network guard in both layouts, because Node 24's model does not restrict sockets. ADR-0006's open item on the flags is answered by this record.
- **A second worker file, `worker/extract.ts`.** The row names `worker/main.ts` only. The dispatch, wire types, sink and typed stop live in `extract.ts` so they can be unit-tested without an IPC channel and so W4-05c/d have a registry to add to; `main.ts` is the three-line entry. Both are under `worker/` and covered by the module-graph test.
- **Wire types defined in `worker/`.** The worker may import only `node:zlib`, `node:buffer` and its own files, so its request and reply types are defined in `worker/extract.ts`, and the host's `protocol.ts` imports them (type-only) and re-exports them; the reply is still checked against the TypeBox schema on the host.
- **Classify on `close`, release on `exit`.** An exit is classified once the IPC channel has drained, so a reply sent just before an exit is still read; the concurrency slot is released when the process has exited, so the cap counts live processes as the plan says.
- **`limit_memory` is read from the exit status** (SIGABRT, or exit code 134), because V8 aborts the process on heap exhaustion and stdio is ignored by design. A native abort for another reason would also read as `limit_memory`; both end as `unavailable:artifact_unreadable` in the runner (plan section 3.1), so no clean result can come from it.
- **`selfTest()` is a round trip, not yet a DOCX.** Plan section 2 says the self-test extracts an embedded synthetic DOCX; no parser exists before W4-05c. Here it is true when a worker starts, reads a probe and answers with a well-formed reply; W4-05c tightens it to the embedded DOCX yielding segments, and W4-13b binds it to readiness.
- **`maxInputBytes` has no policy maximum here.** Plan section 4.4 sets "bytes in ≤ the upload cap"; the host takes the cap as a limit (at least 1) and W4-13b passes the configured `UPLOAD_MAX_FILE_BYTES`, whose own bound is already enforced in `config.ts`. `limits.ts` does not import `config.ts`.
- **`onFork` option.** An observability callback with each worker's PID, used by the one-process-per-call tests (and by W4-10a's "PIDs differ" probe). It carries no content.
- **A TypeScript entry with no loader flag in the parent** gets `--import tsx`, so a source host started without one still forks a loadable worker.
- **Strict wire locators (round 1).** Reviewer finding: the reply schema reused the shared read schema `EvidenceLocatorSchema`, whose variants and region allow extra keys, and only `text` counted toward `maxTextChars`, so a locator could carry a smuggled key or a long heading past `limit_output` into a stored, served locator (decisions 21 and 23). `protocol.ts` now checks locators against its own `WireLocatorSchema` (same five kinds, `additionalProperties: false` on every variant and on `region`, `sheet`/`cell`/`heading` at most `MAX_LOCATOR_STRING_CHARS` = 512). Locator string values (every own string key but `kind`) count toward `maxTextChars` in the worker's `SegmentSink` and in the host's recount, and a string over 512 is `limit_output` on both sides. The shared read schema is unchanged (it is W4-12's read shape; tightening it is out of this ticket). The 512 bound is a working choice under Ta's delegation: long enough for a real heading or sheet name (Excel caps sheet names at 31), short enough that a locator cannot carry a paragraph; W4-05c/d emit through the sink, so they meet it by construction.
- No existing test changed; no spec amendment is assigned to W4-05b. No config key, runner, orchestrator change or migration (W4-13b, W4-06a).
