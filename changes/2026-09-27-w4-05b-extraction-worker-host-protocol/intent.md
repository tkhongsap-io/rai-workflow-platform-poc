# Intent: extraction worker host, protocol and limits (W4-05b, #212)

W4b makes QC read document contents. The bytes it reads are untrusted uploads, so they must never be parsed inside the server process that also holds the database pool and serves every reviewer. This ticket builds the container every document parser will run in, before any parser exists: a host in the server that forks one fresh, short-lived worker process per document, hands it the bytes over IPC, and gets exactly one reply back.

The host fails closed on everything a hostile or broken document can do to a parser. A worker that hangs is killed at the wall-clock limit (`limit_time`); one that exhausts its capped heap is `limit_memory`; one that returns more text or segments than allowed is `limit_output`; one that exits, throws or answers with anything that is not a well-formed reply is `crash`. Input over the upload cap is refused before any fork (`limit_bytes`). A semaphore caps how many workers are alive at once. The worker runs with an empty environment, no stdio and, by test, a module graph that reaches only `node:zlib`, `node:buffer` and its own files: no filesystem, network, child process or database module.

It implements the W4-05b row of the [W4b plan](../../docs/engineering/implementation-plan-w4b.md) (section 4.2 and the limits of section 4.4) under the provisional ADR-0006 (decision 5, WA-D08: a fresh child process per artifact). It also measures fork latency under the source (`tsx`) and built layouts against `QC_EXTRACT_TIMEOUT_MS=4000` and the 10 000 ms deadline, and records whether Node's `--permission` flags work on the fork. The DOCX, XLSX and PDF parsers come in W4-05c and W4-05d; the runner that uses the port in W4-06a; the configuration keys in W4-13b. Synthetic data only; no network call; nothing deploys.
