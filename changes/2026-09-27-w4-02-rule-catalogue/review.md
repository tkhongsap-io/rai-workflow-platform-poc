# Review: versioned rule catalogue keyed by template version (W4-02, #185)

Framed in [intent](intent.md), [spec](spec.md) and [plan](plan.md). Source: [W4a plan](../../docs/engineering/implementation-plan-w4a.md) section 3, with the plan-review notes on the ticket. Decisions implemented: register rows "W4a gate entry", "D05 refinement (upload slot 5 and 9)" and "W4a kickoff rulings" (Ta, 2026-09-26). Synthetic data only; no document parsing, model, provider or network call.

## Change

- **Catalogue body** (`shared/src/schemas/cases.ts`): `QcRulesBodySchema` is now `{ label, templates: { [checklistTemplateVersion]: { rules: QcRuleEntry[] } } }`, each entry `{ ruleId, engine, triggers, severity, params? }`, unknown keys refused. `qcRulesBodyProblems` adds the checks the schema cannot express: `QC-UNAVAILABLE` is refused (orchestrator-only, W0-07 3.6), a rule ID listed twice in one template is refused, and `params` are checked per rule ID (`QC_RULE_PARAMS_SCHEMAS`: `PACK-STAGE-MISMATCH` requires `{ attachedForbiddenAt, notYetForbiddenAt }`, stage to slots 1..9; a rule without a registered schema takes no params). `configuration/store.ts` `validateConfigurationBody` runs both on write.
- **Seed** (`configuration/seed.ts`): `qc_rules` revision 1, label `w4a.1`. `v1.0 Sheet3`: `PACK-SLOT-MISSING` (submit, approve_attempt), `PACK-STAGE-MISMATCH` (submit; `attachedForbiddenAt: { idea: [8] }`, `notYetForbiddenAt: { pre_launch: [1..8] }`), `PACK-NA-VENDOR-DOC` (submit), and the content rules `ACC-METRIC-CITED` (approve_attempt, upload), `ACC-EXTRACTION-NOT-HALLUCINATION`, `ACC-BAND-V1-SHEET3`, `ACC-CLASSIC-ML-METRIC` (approve_attempt). `v2.0`: the same without `ACC-BAND-V1-SHEET3`. Severities follow W0-07 3.5; all provisional until D09.
- **Selection** (`server/src/qc/select.ts`): `selectRules(body, templateVersion, trigger, modelType)` returns the template's rules for the trigger in catalogue order (without `triggers`, `params` deep-copied). `model_type` routing: `ACC-CLASSIC-ML-METRIC` only for `classic_ml`; `ACC-METRIC-CITED`, `ACC-EXTRACTION-NOT-HALLUCINATION`, `ACC-BAND-V1-SHEET3` never for `classic_ml`. An unknown template version (own-property check, so `constructor` or `__proto__` never match) throws `RuleSelectionError('unknown_template_version')`.
- **Revision in force** (`server/src/qc/rules-revision.ts`): `ruleContextOf(exec, version, at)` returns the recorded revision ID and its catalogue. A submitted version reads its frozen revision (`ruleRevisionOf`, unchanged). A draft reads the revision the submit freeze would record at `at` (`revisionsInForce` + `resolveFrozenConfiguration`: published strictly before `at`, `qc_rules` preferred). The revision row is loaded by ID and only a row of kind `qc_rules` yields a catalogue; another kind (a version frozen before W4-02) or no row gives `catalogue: null`. `requestRules` turns the context into `request.rules`.
- **Request** (`shared/src/qc/types.ts`): `QcRunRequest.rules: SelectedRule[] | null`; `SelectedRule = { ruleId, engine, severity, params? }`.
- **Orchestrator** (`qc/orchestrator.ts`): builds `request.rules` from the rule context of the run stamp. A `RuleSelectionError` records the run as `unavailable:runner_error` (detail `unknown_template_version` or `invalid_rule_catalogue`) under the bound runner without calling it, with the usual QC-UNAVAILABLE finding and `qc.run.unavailable` line. The unbound path is unchanged. Replay, retry and the in-flight table are unchanged.
- **Substitutes**: the scripted runner ignores `rules` (new unit test); its test support and the in-memory API substitute set `rules: null` (the API substitute keeps no catalogue, plan section 11).
- **Docs**: dated W4-02 amendments to W0-02 7.3 and 7.6 (`implementation-plan-w1-w3.md`) and W0-07 3.3 (`qc-boundary-and-mail-sink.md`: `request.rules`, the upload revision, `null` versus `[]`, unknown template). `versions/freeze.ts` comment updated.
- **Tests**: new `server/src/configuration/qc-rules.test.ts` (5), `server/src/qc/select.test.ts` (6), `tests/integration/w4-02-rule-catalogue.test.ts` (4); `seed.test.ts` and `w1-05-submit.test.ts` updated (below); one new case in `fixtures/src/substitutes/qc/scripted-runner.test.ts`.

## Deviations

- **`rules: SelectedRule[] | null`, not `SelectedRule[]`.** The plan types the field as an array and says a version with no revision "carries no rules". An empty array must stay a valid zero-rule selection (plan section 5: an upload run evaluates 0 rules and completes), so "no `qc_rules` revision" is `null`. Recorded in the W0-07 3.3 amendment.
- **Who answers `not_configured` before W4-03.** The plan has the deterministic runner answer `null` rules with `unavailable:not_configured`; that runner is W4-03. The required approve-attempt test therefore uses a synthetic probe runner that answers as the plan says the deterministic runner will. It proves the orchestrator side: `rules: null` for a version whose recorded revision is of another kind, the ID still recorded, the outage stored with one reused QC-UNAVAILABLE finding owned by the lane, and a second attempt calling the runner again (retry, not replay). W4-03 adds the runner's own answer.
- **Unknown template recorded before the runner.** The plan says an unknown template makes the run `unavailable:runner_error` (`unknown_template_version`). Selection happens in the orchestrator, so the run is recorded there under the bound runner's identity without calling it, like the unbound path; no `qc.run.started` line is emitted because the runner never starts. This applies whatever runner is bound; no fixture case uses a template missing from the seed.
- **Stored body that fails the schema.** Not in the plan. Bodies are validated on write, so this only guards against a body written under an older schema: the run is `runner_error` (`invalid_rule_catalogue`), never a clean pass.
- **A draft with no `qc_rules` revision in force** records what the freeze would record at that instant (the view-kind revision), which QC reads as no rules. W4-04 wires the upload trigger; W4-02 provides and tests `ruleContextOf` on a draft.
- **`model_type` routing lives in `select.ts`** as a rule-ID table, not in the catalogue body: the plan's body type has no model-type field and states the routing as a fixed rule.
- **`PACK-NA-VENDOR-DOC` severity** is `medium`: the plan gives none, and W0-07 3.5 sets `medium` for every rule not named `high`. Provisional until D09; W4-03 may revise it with its rule rows.
- **`PACK-STAGE-MISMATCH` params shape** (`{ attachedForbiddenAt: { idea: [8] }, notYetForbiddenAt: { pre_launch: [1..8] } }`, stage to slot list) is the smallest encoding of the plan's matrix `{ attachedForbiddenAt, notYetForbiddenAt }`; lane-gated slots are 1-8 (D02 `noLaneGate: [9]`).
- **Changed expectations in existing tests** (the plan's behaviour change, section 3):
  - `server/src/configuration/seed.test.ts`: the seeded kinds now include `qc_rules`, and the assertion that `qc_rules` is absent is replaced by a test of the catalogue content.
  - `tests/integration/w1-05-submit.test.ts`: `configurationRevisionId` (response and row) is now the seeded `qc_rules` revision, and differs from `ConfigurationView.revisionId`; the view's revision is still asserted to be among the frozen kinds, and `frozen_configuration.qc_rules` equals the FK. No assertion was removed.
- **W4-11a distinguishability test** replaces a version's frozen `qc_rules` with a random UUID. With W4-02 that ID names no row, so the request carries `rules: null`; the probe ignores rules and the test is unchanged and green.
