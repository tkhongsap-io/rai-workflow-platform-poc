# Intent: versioned rule catalogue keyed by template version (W4-02, #185)

Today the `qc_rules` configuration kind has a placeholder body (`{ rulesRevision }`) and no revision is ever published, so every version freezes a configuration revision of another kind and QC runs record that ID as their rule revision. The runner is told nothing about which rules apply. W4a needs a real catalogue so the deterministic runner (W4-03) can execute the metadata rules of the version's checklist template, and so a run can show which rules and which revision it applied.

This ticket gives `qc_rules` its W4a body (a human `label` and rules per `checklist_template_version`), seeds revision 1 (`w4a.1`) for `v1.0 Sheet3` and `v2.0`, and makes the orchestrator load the catalogue by the recorded revision ID, select the rules for the template, trigger and model type, and pass them to the runner as `request.rules`. `v2.0` never selects the v1.0 Sheet-3 bands. A version without a `qc_rules` revision is sent no rules, so the deterministic runner can answer `unavailable:not_configured` instead of a clean pass. It is the second W4a ticket (plan section 9, order 2) and implements [W4a plan](../../docs/engineering/implementation-plan-w4a.md) section 3 under the register rows "W4a gate entry", "D05 refinement (upload slot 5 and 9)" and "W4a kickoff rulings" (Ta, 2026-09-26).

No rule is executed here (W4-03), no upload trigger is wired (W4-04) and nothing is shown in the UI (W4-12). The bundled scripted substitute ignores `request.rules`, so every existing suite, which binds it, behaves as before. Rule severities and lists are provisional until D09. Synthetic data only.
