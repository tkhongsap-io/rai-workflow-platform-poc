# Intent: evaluation harness core and report (W4-08a, #237)

W4-09a gave the team a synthetic evaluation set (`qc-eval-synthetic@1`, dev split: 26 cases, their documents and the provisional labels of every run part each trigger should record). W4-06a-c gave QC a content runner with four content rules. Nothing yet measures the runners against the labels the way the evaluation plan asks: per rule and per segment, with false positives and negatives, grounded citations, unavailable handling, latency, failures and cost, under a recorded identity of everything that produced the numbers.

This ticket builds that harness. `npm run eval:qc -- --split dev` runs, in process and without a database, both run parts of every labelled trigger (upload, submit, one approve attempt per lane): the W4a deterministic runner and the content runner over the real forking extraction worker, each request built the way the orchestrator builds it and each result passed through the orchestrator's own boundary checks. It grades the results against the labels and writes `report.json` and `report.md`: identities, hashes, locators and counts only, never document text. The report records the code commit, runner and extractor versions, the rules label and body digest, the template versions, the prompt revision and model identity (disabled), the dataset identity, the grader version and the thresholds file digest, and one `identityDigest` over all of them.

To build requests and check results exactly as the product does, the pure part of the orchestrator's `buildRequest` moves to `server/src/qc/request.ts` and `checkedResult` (with `unavailableResult` and `callRunner`) to `server/src/qc/check-result.ts`. Both are moves: the orchestrator imports them and behaves identically; existing tests are unchanged.

It is W4b ticket 21 (track T5, lane C) and implements the [W4b plan](../../docs/engineering/implementation-plan-w4b.md) section 15 row W4-08a and sections 11.2 and 11.3, under the register rows "Ta's delegation (2026-09-27)" and "W4b delegated rulings (provisional)". The threshold gate, the stale check (`--verify`) and the CI step are W4-08b; the held-out split is W4-09b. D07-D10 stay open; the thresholds and labels are provisional (WA-D09). Synthetic data only; no network call; no model; no migration.
