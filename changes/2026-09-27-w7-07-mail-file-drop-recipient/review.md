## Deviations

- **Parity and re-export test in fixtures.** The plan puts the `MailSinkFile` shape test in `server/src/notifications/file-drop.test.ts`. The server package cannot import `@rai/fixtures` (fixtures references server in `tsc -b`, and the server never imports fixtures statically), so the cross-sink parity, the `MailSinkFile` parse and the re-export identity live in `fixtures/src/substitutes/mail-sink/file-drop-parity.test.ts`, which may import `@rai/server`. The server test keeps every section 4.8 row that needs no fixture code.
- **`no-external-mail.test.ts` allow-list pattern gains `-`.** The rule allowed `@rai\/shared\/[a-z/]+`; the plan's file name `@rai/shared/mail/file-stem` has a hyphen. The pattern is now `[a-z/-]+`. The transport-built-in and mail-SDK assertions are unchanged, and the walked set grows by `file-drop.ts`, so the check is stricter overall.
- **Health does not call `writableDirectory`.** The plan says readiness probes the drop with `observability/probes.ts` `writableDirectory`. That helper reports a missing directory as `unreachable` and never creates it, so a fresh `MAIL_SINK_DIR` would hold readiness at 503 until a first delivery; and importing `probes.ts` would pull `pg` into the sink module. `health()` creates the directory 0700 and checks `W_OK`, as `FileMailSink.health()` does.
- **The live directory exists only when the drop is bound.** With `sink-memory` outside `fixture` mode nothing is bound (plan: "today's behaviour"), so the directory is not loaded and recipients stay empty, as today; otherwise submits would enqueue outbox rows no sink could deliver. The directory filters profiles by the running identity mode, so rows left by an earlier configuration (other subject IDs) are never recipients.
- **A failed start-up load does not refuse start.** The plan says the load is awaited before `listen` and names no failure rule. Refusing (exit 78) would turn a database outage into a configuration refusal, while today a desk with its database down still starts and reports readiness 503. The failure is recorded as `error.captured` once the app's error capture exists, and the directory retries the load in the background on the next read (one at a time, reported the same way). No new log event.
- **`RecipientDirectory` members are function properties**, so consumers take them unbound (`recipients.identities`) without the `unbound-method` lint rule firing.
- **`IdentityAdapter.configuredGrants()` is required**, so the one hand-written adapter fake (`observability/http.test.ts`) gains `configuredGrants: () => []`; no assertion changed.
- **Integration composition.** The OBS15 policy (`tests/support/integration-log-policy.ts`) forbids integration files from importing `start.ts`, so `w7-07-file-drop.test.ts` builds the `start.ts` composition from its parts (`createFileDropMailSink`, a loaded live directory, `composeAppDeps`, the observed `buildApp`, the same readiness reader); the `start.ts` binding itself is covered by the `start.test.ts` table.
- **File modes.** The drop writes files 0600 in a 0700 directory as the plan says; the fixture `FileMailSink` keeps its umask default (unchanged), so the parity test compares names, JSON and receipts, not modes.
- **W0-07 amendment placement.** The plan names "W0-07 section 5"; the note is a dated section at the end of W0-07 that names the sections it amends (4.3, 4.6, 4.7, 5), as the earlier amendments do.
- **Lane environment.** `rai-web/.env` (never committed) sets `RAI_PG_TOOLS=docker-compose:rai-ops`, as W7-01 to W7-06 did.
