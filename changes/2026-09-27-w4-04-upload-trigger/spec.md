# Specification

Source: W4a plan section 5 (the plan wins over issue #188), section 8 (commands), section 12 (amendments), with the plan-review notes on the ticket.

Done when:

1. **Target.** A new `loadUploadTarget` (in `qc/orchestrator.ts`) accepts the case's open draft, or the version that draft became while it is still open (current, not Ready, not closed by a send-back). `loadOpenSubmittedTarget` is unchanged. The request uses the row's `checklist_template_version`, the `qc_rules` revision of plan section 3 (in force at the upload instant for a draft; frozen for a submitted row) and, for a draft, the current lane-mapping constant.
2. **Request scope.** `slots` holds the one uploaded slot and `artifacts` its artifact (W0-07 3.3 "one for upload"); `runKey` is W0-07 3.7's (version, trigger, `-`, revision, `slot:contentHash`).
3. **Run fields.** An upload run row has `trigger = 'upload'`, `lane = NULL` and `slot` set. Upload never replays: every trigger is a new run. The in-flight table for upload is keyed by `runKey`, so two attaches in one save run separately.
4. **Owning lane.** `unavailableOwningLane` gains an overload: submit and approve-attempt callers keep the non-null `Lane` return; `{ trigger: 'upload', slot }` returns `Lane | null`: the single lane for slots 1-4 and 6-8, `ai_coe` for slot 5 (register row "D05 refinement (upload slot 5 and 9)"), `null` for slot 9. The upload trigger checks it before calling the orchestrator: a slot-9 attach writes no `qc_run` row. `observability/operator.ts` resolves the owning lane of an unavailable upload run the same way (from `qc_run.slot` and the version's mapping, or the current one for a draft).
5. **Outage reuse.** An upload QC-UNAVAILABLE finding is reused per version and owning lane (`QC-UNAVAILABLE:run:upload:<owningLane>`): a repeat outage on the same lane while its finding is undispositioned appends a run row and reuses the finding; an outage on another lane appends a new finding.
6. **Where the result lands.** Draft still open → appended to the draft row. Draft submitted, version open → appended to that version; a carried upload outage keeps Ready from being reached (A08). Version Ready → late: nothing written, `qc.run.late` and a `qc_late_result` row as for submit. Version closed by a send-back → refused `version_closed`: nothing written.
7. **Wiring.** `pack/qc-trigger.ts` `createUploadTrigger` is bound in `app.ts` (next to the submit trigger) from `AppDeps.pack.qc`, which `compose-app-deps.ts` fills when a runner is bound. `pack/service.ts` `fireUploadTriggers` tracks each fired promise on the app drain, so `drain.close()` waits for an in-flight upload run. The save-draft response never waits for QC. One run per changed attach, none on an unchanged save.
8. **Substitute.** The `upload` entries leave `fixtures/src/substitutes/qc/scripts/fx-case-nonvendor.json` and `fx-case-vendor.json`; `scripted-runner.test.ts` and `scripts.test.ts` are rewritten for that (the slot-scoping behaviour stays tested with an inline script); the zero-finding answer for an unscripted trigger is unchanged.
9. **Deterministic runner.** A completed upload run records `rules_evaluated = 0` and no finding.
10. **Tests.** Unit: `unavailableOwningLane` upload cases. Integration (real Postgres): one run per changed attach, none unchanged, two attaches run separately, slot 9 none, response does not wait, drain waits, slot-5 outage to AI/COE, per-lane reuse, a run completing after submit appends to the version, carried outage gates Ready, Ready → late, send-back → nothing written, operator view lane for an upload outage. Real server: `w4a-int-deterministic-server.test.ts` attaches over HTTP and sees one upload run with `rules_evaluated = 0`.
11. **Docs.** Dated W0-07 3.2, 3.6 and 3.9 amendments.
12. Full plan section 8 gate green.
