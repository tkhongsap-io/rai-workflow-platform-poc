# Intent: upload-trigger QC on the save-draft attach (W4-04, #188)

W0-07 3.2 defines three QC triggers. `submit` and `approve_attempt` run; the `upload` trigger has been a hook point since W1-04 (`pack/qc-trigger.ts`) with a no-op bound, and its promise is not tracked by the shutdown drain. This ticket binds it: an attach that changes a slot's artifact reference on a save-draft fires one QC run on that slot, recorded on the draft row (which becomes the version at submit), after the save commits and without the save response waiting for it.

It is the fifth W4a ticket (plan section 9, order 5) and implements [W4a plan](../../docs/engineering/implementation-plan-w4a.md) section 5 under the register rows "W4a gate entry", "D05 refinement (upload slot 5 and 9)" and "W4a kickoff rulings" (Ta, 2026-09-26): an upload outage on slot 5 is AI/COE's, and slot 9 gets no upload run and no finding. With the deterministic runner no W4a metadata rule has the `upload` trigger, so an upload run records `rules_evaluated = 0` and stores no defect; the point of the ticket is the plumbing, the outage ownership and the version-closure rules, which W4b's content rules will use. The scripted substitute loses its bundled `upload` entries (upload content rules are W4b's) so that CI, which binds it, does not start writing scripted findings on every re-attach.

Human-review-required: it touches immutability (where a late run may land), the Ready gate (a carried upload outage) and shutdown (the drain). Not here: the qc-runs endpoint and QC log UI (W4-12), finding dedup (W4b), any content rule, parser, model or provider. Synthetic data only.
