# Specification

Source: the W4-05d row of section 15 of the [W4b plan](../../docs/engineering/implementation-plan-w4b.md), section 4.3 (formats), section 4.4 (limits), decisions 8, 21 and 23, the unit layer of section 17, and the provisional [ADR-0006](../../adr/0006-qc-engine-and-extraction.md). The plan wins over issue #227. No spec amendment is assigned to W4-05d.

Done when:

1. **Container** (`worker/pdf.ts`): the file starts with `%PDF-` and has `%%EOF` in its last 1 024 bytes. The last `startxref` in that tail points at a classic `xref` table. Its subsections are read, then its `trailer` dictionary, then any `/Prev` tables (newest entry wins, a cycle or a bad offset is `unreadable`). A `startxref` that points anywhere else, including at a cross-reference stream (object streams only), is `unreadable`. A trailer with `/Encrypt` is `unreadable`. More in-use entries than 100 000 objects (`maxPdfObjects`) is `limit_output`.
2. **Objects**: an indirect object is read at its xref offset, which must hold `n g obj` for the same number and generation; otherwise the xref is broken and the file is `unreadable`. The object grammar is numbers, names (with `#xx`), literal strings (nesting, escapes, octal), hex strings, arrays, dictionaries, references, booleans and null, nested at most 64 deep. A stream's `/Length` (direct or indirect) must end its data right before `endstream`. Any grammar error is `unreadable`.
3. **Pages**: from the trailer `/Root` catalog's `/Pages`, the tree is walked in order (`/Kids`, cycle guarded, at most 64 levels). `/Resources` is inherited. More than 2 000 pages (`maxPdfPages`) is `limit_output`.
4. **Content streams**: a page's `/Contents` is one stream or an array of streams, read in order. A stream with no filter is read as is; `/FlateDecode` (a name or a one-element array, no predictor) is inflated with `maxOutputLength` = 20 MiB; any other filter makes that stream unread. A decoded stream over 20 MiB, or more than 100 MiB decoded per artifact, is `limit_bytes`; a stream that fails to inflate is `unreadable`.
5. **Text**: the content lexer skips inline image data. `Tj`, `TJ`, `'` and `"` show strings; a string starting with `FE FF` is UTF-16BE, any other is Latin-1, and C0/C1 control characters other than tab are dropped. A string shown in a font whose `/Subtype` is `/Type0` (a CID font) is not decoded. In `TJ`, an adjustment of -200 or less inserts a space. Lines: `T*`, `'` and `"` start a new line; a text-showing operator whose line-matrix vertical position differs from the current line's starts a new line; a text position move on the same line inserts a space before the next string. Each page's non-blank lines become one segment each, `{ kind: 'page', page }` with a 1-based page number, in page order.
6. **Unreadable when** (section 4.3): `/Encrypt`; object streams only; other filters on every content stream (no text); a broken xref; no text on any page (a scan); or an active-content name (`/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile`, `/RichMedia`, `/XFA`), which the upload already refuses (defence in depth).
7. **Registry**: `application/pdf` registered in `FORMAT_EXTRACTORS`; `image/png` and `image/jpeg` stay unregistered and are always `unreadable` (no OCR, decision 8).
8. **Hostile set**: every W0-08 hostile row under the PDF media type ends as a clean reply, never a throw; every refused row is `ok: false`, and the PDF rows are refused even over a text-bearing PDF. Encrypted, image-only and broken PDFs are `ok: false` through the real forked worker.
9. The worker module-graph test stays green (`node:zlib`, `node:buffer` and `worker/` only). The extractor reads the W4-09a evaluation set's text PDFs (plain and FlateDecode) at the page locators the renderer records for each claim, and the image, CID and broken-xref renderings are `unreadable`.
