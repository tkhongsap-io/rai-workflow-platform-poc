## Deviations

- **A failing `profiles.recorded` hook does not fail the sign-in.** The plan says only that `establishSession` calls the hook after `create` resolves. At that point the session, the audit row and the profile have committed and the cookie is set; answering 500 would leave a signed-in browser that was told sign-in failed. The error goes to the app's existing `errors.internal` (`error.captured`, route `/auth/callback`, no values), and the sign-in answers as usual. No new log event.
- **The profile's email and name come from the principal.** The plan says "from the verified login and principal". The principal is minted from the verified login by `principalFrom` (email lower-cased and trimmed; display name the allow-list override when one exists, else the login's `name`, else the email local part, capped at 200), so the profile holds exactly what the session's principal holds.
- **The upsert refreshes `identity_mode`, `email` and `display_name` as well** as `last_sign_in_at` and `roles` (the plan names the last two). A person's name or address can change at the provider; the directory should name them as they last signed in. `first_seen_at` is never updated.
- **Memory store mirrors the CHECK.** The memory store rejects a fixture-mode profile so the unit contract matches the Postgres store (the plan asks for "one contract").
- **`w7-03-migration-classes.test.ts` helper `releaseLength()` redefined (test support, no assertion changed).** It chose "the longest journal at or after W7-03 whose newest migration is additive" as the release the rollback tests start from. With this ticket's additive `0013` after W6-02's restore-required `0012`, that release became the whole journal, so `additivePrefix()` stopped at `0012` and the pre-W7-03 target case failed its precondition (`'the pre-W7-03 journal'`), although nothing about rollback behaviour changed. The release is now the W7-03 migration plus the longest unbroken run of additive migrations after it (today `0000`-`0011`, the same prefix the test used before W6-02 and this ticket), which keeps every assertion and its meaning whatever later migrations are classed; the helper's comment says why.
- **Migration slot: queued, not held.** W7 plan section 9.1 allows one migration-bearing PR in review at a time, holding `MIGRATION-SLOT` on `docs/board/lane-lead-integration.md`. W4-11b (#201, PR #282) is still open with a migration; this PR files a queued `MIGRATION-SLOT` claim (2026-09-28 03:39) and must not merge while another migration PR holds the slot. Before merge it rebases onto current `main`, regenerates its migration by hand at the next free number (keeping the header, grant and `MIGRATION_CLASSES` entry, plus entries for any migration merged first), unions the `w1-00-migrations` lists, and reruns the full gate.
- **Lane environment.** `rai-web/.env` (never committed) sets `RAI_PG_TOOLS=docker-compose:rai-ops` (the lane's compose project), as W7-01 and W7-03 did; with the `.env.example` value `docker-compose:rai-dev` the W7-01/W7-02 backup tests fail with `pg_tools_container_not_found` because no `rai-dev` container runs in this lane.
