# H17: concurrent reuse of one Idempotency-Key across two cases returns 422, not 500

## Finding addressed

- **workflow-core resilience (low).** `withWorkflowTransaction` serialised only on the case row. When one actor sent the same `Idempotency-Key` to two cases at the same moment, the two case locks were different. Both transactions found no stored key, and the second one to reach `storeIdempotencyKey` failed on the `idempotency_key` primary key. The client got `500 internal_error` instead of the contract's `422 error.invalid_input.idempotency_key_reused` (W0-06 5.3). Still reproduced on main `d815a8e`: the new test got `[201, 500]`, three runs out of three.

## Change

- `rai-web/server/src/versions/transaction.ts`: after `lockCase` and `readCaseRow`, and before `validate` and `findReplay`, the transaction takes the existing `lockIdempotencyKey(tx, actor, key)` advisory lock from `cases/idempotency.ts`. The second request now waits for the first to commit, finds the stored key with a different digest and answers 422. The header comment is shorter: the ticket-history asides are gone, and it now states the lock order.
- Lock order: the case lock comes first, then the key lock. Create-case takes only the key lock, and the case row it inserts is new, so no transaction holds the key lock while it waits for an existing case lock. No lock cycle is possible.
- `rai-web/tests/integration/w3-hardening-idempotency-race.test.ts` (new): the owner submits `fx-case-vendor` and `fx-case-nonvendor`. The DPO runs lane QC on each (real `runId`s), then sends both approvals in `Promise.all` under one key. The test expects one 201 and one 422 at `header.idempotency-key` with `idempotency_key_reused`, and exactly one `lane_decision`. The only `error.captured` line allowed is the 422's `invalid_input` capture (every 4xx logs one), so no `internal_error` is captured. Before the fix the test fails with `[201, 500]`. After the fix it passes, five runs out of five.
- `docs/engineering/persistence-and-artifact-store.md` ("Transactions and idempotency"): the sketch shows the key lock, and the sentence "actions on different cases do not block each other" now names this exception. This is an edit outside the batch's file list. H8 owns a different section of the same file (the column note), so the two edits should merge cleanly.

## What got smaller

`transaction.ts`: 10 header lines became 9, and there is one added call and one added import name. No new helper; the change reuses the create-case lock.
