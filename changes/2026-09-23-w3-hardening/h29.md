# H29: Draft editor only for users who can edit; no stale 'Draft saved' notice on another version

The final walkthrough re-verification on main `dfe84b3` found both issues. Both still reproduced on `dfe84b3`: the new browser assertions below failed before the change.

## Findings addressed

- **The draft editor's Change, Save and Submit controls were shown to users who cannot edit the draft (medium).** Admin, every lane reviewer, and the DPO + HR SPOC on a CM case (RAI-2000-0003, where she is not SPOC) all saw the full editor. The server answered their `PUT` with 403. Now the case screen passes `canEdit` to `PackEditor`, and only a writer of the case gets the controls. `canEdit` comes from the web predicate that already expressed the W0-05 `WRITE_ROLES` rule on a case: an owner grant on the case's business owner, or a `bu_spoc` grant for its BU. That predicate was named `canProposeFixedOnCase`. It is now `isCaseWriter`, because it serves edit, submit and propose-fixed alike. There is no second copy of the policy table. Anyone else sees the settings as a disabled fieldset, the nine slot rows with their files, and one line: `pack.read_only` ("Only the case owner or the business unit's SPOC can change this draft", in both catalogues). They get no Change, Save, Discard or Submit control.
- **'Draft saved (revision N)' carried over onto the version 1 page (low).** Each `Notice` now names the route it belongs to (`versionId`, undefined for the draft). A route change clears the notice unless it names the new route. The submit notice names the version it opens, so "Version N submitted" still shows there. This replaces the editor's `key.startsWith('pack.')` filter.

The server is unchanged. It is still the authority, and the new browser test checks that a reader's forced `PUT` is still refused with 403.

## Fix round 0: combined-CI failure after H28

After H28 (#156) merged, H29 was rebased onto `23b02b6`. CI run 36021174866 on that head (`ebd57d5`) failed one test at desktop-1440: `w3-int-journey` "one keyboard case …". The failure was in `signOut` (spec line 231), just after the AI/COE reviewer sends v1 back. The locator `getByRole('dialog').getByRole('button', { name: 'ออกจากระบบ' })` found nothing within 5 s. Tablet and phone passed.

**Cause.** A lane decision raises a notice and reloads the case screen. While the reload runs, the decision controls are unmounted and focus falls to `<body>`. When the reload lands, the notice mounts and a ref callback focuses it. That callback ran every time, so it also took focus from any control the user had reached in the meantime. In the journey, the test had already tabbed from `<body>` to the shell's sign-out button when the reload finished. The notice took focus, and the Enter meant for sign-out went to the notice paragraph. The sign-out dialog never opened. The race is in the product, not in the test. It exists on `23b02b6` too; H29 does not touch this code. After a send-back the reload also reads the successor draft, which took 311 ms in CI, so the window was wide enough to hit.

**Evidence from the CI trace** (the `playwright-report` artifact of run 36021174866, desktop-1440):
- The send-back POST answered at about 383.69 s. The reload started at 383.70 s and its `GET …/draft` took 311 ms.
- Tab presses from 383.79 s: the first found `<body>` focused. The test reached sign-out at 384.06 s and checked it again at 384.10 s.
- Every DOM snapshot from 383.77 s to 384.10 s shows the loading state. The snapshot taken during the Enter press (384.12 s) is the first with the loaded case screen and the notice `ส่งกลับให้แก้ไขแล้ว และเปิดฉบับร่างรุ่นถัดไป`.
- The failure snapshot shows the notice and no dialog.

**Reproduction.** Locally the journey passed 8 of 8 at desktop-1440 (`--repeat-each 8`), because the reload finished before the test reached sign-out. The new browser test below forces the order: it holds the reload until the keyboard user has reached sign-out. It failed at all three widths on `ebd57d5` (`toBeFocused`: "inactive"). It also failed at 1440 with the UI code of `23b02b6` checked out, so the race predates H29.

**Fix.** The notice takes focus only when focus has dropped to `<body>`. The ref callback is renamed from `focusOnMount` to `focusIfDropped`. When nobody moved focus, the decision still lands focus on its outcome. The existing checks that the approve and send-back notices are focused still pass. The journey spec is unchanged; no wait, sleep or retry was added.

**Test (fails before, passes after).** `tests/browser/w2-int-07-reviewer-workspace.spec.ts` has a new test, "the decision notice does not take focus from a control the keyboard user reached during the reload". It holds `GET /api/cases/:id` with `page.route`, approves, and waits for the loading state. It tabs to the shell's sign-out button, then releases the reload and waits for the approve notice. Sign-out must still hold focus, and Enter must open the sign-out dialog.

**A second flake found by the full local run.** The first full `npm run test:browser` after the fix failed one test: `w1-int-07` "the whole journey runs on the keyboard alone …" at desktop-1440. Line 412 raised "no element is focused". The trace shows why. Tab went from the source-record radios to the vendor radios, then the model-type radios, the Create button, Cancel, and `<body>`. It skipped the use-case group select. The screencast frame taken while the technical owner was typed shows that select still reading "กำลังโหลด…", disabled, because the new-case screen had not yet received its configuration. The run was fast enough (about 1 s for the whole test) that the keyboard walk overtook the load. The fix is in the test, which now waits for the select to be enabled before it tabs through the form. The product already behaves correctly here: while the options are missing the select stays disabled, and Tab skips it. Neither H28 nor H29 touches that screen. After the wait the test passed 15 of 15 (`--repeat-each 5`, three widths).
