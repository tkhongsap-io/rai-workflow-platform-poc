# H3: One derived case status, plus queue and SLA correctness

Batch H3 of the [W3 hardening](intent.md). Synthetic data only.

## Findings addressed

1. **`awaiting_disposition` appeared only in the queue** (queue-sla, bug, high). `/api/cases` and `/api/cases/:id` reported a case with three approvals and an open finding as `in_review`. The queue's SQL `CASE` moved to `cases/status.ts` as `caseStatusSql(current, draft)`. It is now the only status derivation, and the queue, `listCases` and `caseViewFrom` all use it. `caseViewFrom` reads the status and both version rows in one left-joined select through the caller's executor, so inside the create or edit transaction it sees the row just written. `deriveCaseStatus`, `StatusInputs` and their unit tests are deleted. `deskStatusFor` stays. In `w3-01-queue`, the `awaiting_disposition` step now asserts `GET /api/cases/:id` `.status` and the `GET /api/cases` item status. Before the fix both returned `in_review`.
2. **`desk_status` was not updated on send-back, and `deskStatusFor` was dead** (workflow-core, bug, low). When `writeLaneProjection` links a newly created successor draft it now also sets `deskStatus = deskStatusFor('sent_back')` (`draft`). Its last parameter is now `successorDraftId?: string`, because no caller passes `null`. Submit (`versions/repository.ts`), Ready (`workflow/ready.ts`) and create (`cases/repository.ts`) also write through `deskStatusFor`, so the helper is the one mapping. The `w3-01-queue` send-back step asserts `desk_status = 'draft'`. Before the fix it was `in_review`.
3. **N+1 per queue card and per open case** (queue-sla, resilience, low). `sla/due-dates.ts` adds `dueDatesFor(exec, version, memo)`. It reads each frozen (sla, calendar) revision pair once per memo and still fails closed with `FrozenSlaUnavailable` for the version at hand. `laneDueDates(exec, versionId)` stays a thin wrapper, so `notifications/service.ts`, `notifications/digest.ts` and the tests are untouched. The queue selects the current version's `submitted_at` and `frozen_configuration` in its `visible` sub-select and shares one memo per request, so the extra version read per card is gone. `listSlaBreaches` shares one memo across targets and uses `dueDatesFor`, which replaces `frozenSlaCalendar`.
4. **The breach query's exclusion rules had no tests** (queue-sla, test-gap, low). New `w3-05-sla` test: VENDOR and NONVENDOR are submitted on one clock, and dpo is approved (a real lane-QC run, then approve) on NONVENDOR. At 2026-04-22 the breaches are exactly VENDOR dpo (due 2026-04-17), then the four 2026-04-21 lanes ordered by case ID and lane. The approved lane is absent. After ai_coe and it_security approve, NONVENDOR is Ready and drops out. `working-days.test.ts` gains a Saturday-in-Bangkok open (`2026-09-25T17:30Z`, 3 days, due 2026-09-30) and a New Year's Eve open with holidays `2026-12-31` and `2027-01-01` (3 days, due 2027-01-06). These tests pin behaviour that was already correct, so they pass before and after the change.
5. **The owner filter showed opaque subject IDs** (web-ui, bug, low, owner-filter part only). `filterOptions.owners` is now `{ value, label }[]` (`QueueOwnerOption` in `shared/src/schemas/queue.ts`). `value` is the owner subject ID the `owner` filter matches, and `label` is the `business_owner` name the cards show. The SPA renders `<option value={o.value}>{o.label}</option>`. The server groups by `owner_subject_id` with `min(business_owner)` rather than `selectDistinct` on both columns. After a provider-side display-name change, one owner could otherwise appear twice with the same option value. The API substitute and the performance harness's expected-queue model follow the same shape. The CaseView and version display names and the run ID stay as they are, as the finding says.
6. **Dead exports in `cases/`** (queue-sla, simplify). Deleted `caseInScope` and its test, the `export { eq }` re-export in `scope.ts`, and the `SLOT_NUMBERS`/`VENDOR_SLOTS` re-export in `cases/repository.ts`.
7. **Headers narrated history and some were false** (queue-sla, simplify). The `status.ts` header now states the rule. The `cases/repository.ts` header names who writes lane projections and readiness, and says every status comes from `caseStatusSql`.

**Flagged for the owner, not changed.** `scopedCases` in `cases/scope.ts` has no caller, and the lint rule its spec promises does not exist. W0-04 Interfaces names it, so this batch leaves it in place.

**Observable change.** `/api/cases` and `/api/cases/:id` now return `awaiting_disposition` for approved cases that still have an undispositioned finding, as W0-06 2.4 says. Any client that still reads `filterOptions.owners` as `string[]` breaks. The SPA, the substitute and the performance harness change in this PR.

## What got smaller or clearer

- There is one status derivation (SQL) instead of two. The TypeScript copy could not see findings.
- `caseViewFrom` makes one query where it made two version reads.
- The queue no longer reads the version again per card. Breach and queue reads fetch each frozen revision pair once per request.
- `scope.ts` shrinks from 82 to 60 lines and `status.test.ts` from 45 to 13. `breach.ts` no longer computes due dates itself.
- `frozenSlaCalendar` is no longer exported; `dueDatesFor` is the one entry point.
