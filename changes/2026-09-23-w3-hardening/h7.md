# H7: QC orchestrator fails closed on invalid or unmappable findings; runQc simplified

## Findings addressed

1. **workflow-core (bug, medium): the orchestrator silently dropped invalid, lane-mismatched and slot-5/9/pack findings and recorded a clean `completed` run.** `storeableFindings` skipped every finding that failed `validateQcFinding` or `checkOwningLane`, so a real slot-5, slot-9 or pack-level defect, or a runner that mislabelled a lane, disappeared from a run that still read as clean. It also settled issue #35 by default, treating every pending category as informational only. W0-07 3.4 steps 4 and 5 already say that any violation makes the run `unavailable:runner_error`. The code now does that:
   - `checkedResult` runs right after the runner returns and before persisting. It checks every finding with `validateQcFinding(finding, request)` and then `checkOwningLane` against `LANE_MAPPINGS_BY_VERSION[request.laneMappingVersion]`. An unknown mapping also fails, as `owning_lane_rule_pending`. On the first violation the result becomes `unavailable`, reason `runner_error`, with the violation name in the in-memory `detail`. The existing unavailable path then records the `qc_run` row with 0 findings, returns the unavailable outcome and emits `qc.run.unavailable` with reason `runner_error`. No `detail` field is logged, because W0-10 3.3 does not list one.
   - `storeableFindings` is deleted, including its redundant slot and `refinement_pending` re-checks.
   - Reproduced before the fix. The new W2-05 test `a slot-5 or lane-mismatched runner finding records the run unavailable runner_error with no findings` got `status: 'completed'` with `findings: []`. It passes after the fix. Its control case, a valid slot-2 DPO finding, is still stored.
   - **Issue #35 stays open. This batch does not decide it.** Slot-5, slot-9, pack-level and other `refinement_pending` findings get no owning lane. A run that produces one is recorded as `unavailable`, which the reviewer sees and which W0-06 accepts for approve. The W1-10 substitute scripts no such finding, so nothing changes in slice 1. A real QC engine (W4) that produces one will show as unavailable until #35 is decided.
   - A late result (one that arrives after Ready) that is also invalid is now recorded in `qc_late_result` as `unavailable` with 0 refused findings, because validation runs before the persist step (W0-07 3.4 orders step 4 before step 6). The W2-05 test `an invalid finding that arrives after Ready is recorded late as unavailable with no refused findings` pins this. With validation moved back into the persist transaction it fails (`status: 'completed', refused_finding_count: 1`); as the code stands it passes.
2. **workflow-core and architecture (simplify, low; duplicates): `runQc` was about 230 lines, with a duplicated replay branch, guards for impossible states and a silent lane-mapping default.**
   - `buildRequest` throws when `laneMappingVersion` is null. It no longer falls back to `?? 'lane-mapping/v1'`. Submit freezes the mapping, so a submitted version always has one.
   - Both `setWorkflowWrite` calls are removed from the QC transactions. They write only `qc_run`, `qc_finding` and `audit_event`, never a `case` projection, so the projection gate stays armed. The late-diagnostic transaction never had one.
   - `replayPrior(tx, input, version, runnerBound)` holds the W0-07 3.7 replay rule once. The prepare transaction passes `runner !== undefined` and the persist transaction passes `true`, which reproduces both old copies exactly. A new test pins the unbound-runner behaviour: an unbound runner replays its own `unbound` row, a bound runner retries after it, an unbound runner after a bound runner's unavailable row records a new `unbound` row, and a completed run replays for any runner. It was written and passed before the refactor, and it still passes after.
   - The prepare step returns a discriminated result (`replayed`, `recorded` or `ready`), and `ready` carries the runner. The `runner === undefined` throw and the `'recorded' in` check are gone.
   - `recordRun(tx, version, request, run, unavailableReason, findingCount)` inserts the `qc_run` row and the `qc.run_recorded` audit event for both persist paths. `persistResult` replaces `persistCompleted` and `persistUnavailable`, and the unbound path uses it too. The `upload`-only slot expression is gone, because `runQc` never runs the upload trigger.
   - `callRunner`, `settle` (emits the completion line only for a newly recorded run) and `recordLate` come out of `runQc`, which is now 58 lines.
