# H11: fail closed on operator retention thresholds and on submissions without a frozen SLA/calendar

## Findings addressed

1. **runtime-ops (bug, medium): the operator cleanup commands parsed their thresholds fail-open.** `db:cleanup` read `Number(env.IDEMPOTENCY_TTL_HOURS ?? '72')` and `store:cleanup` read `Number(env.BLOB_TMP_MAX_AGE_HOURS ?? '1')`. An empty placeholder gives `Number('') === 0`, so `db:cleanup` expired every idempotency key (a retry inside the 72 h window re-executes instead of replaying, A07) and `store:cleanup` removed every staging file, including an in-flight upload's. Reproduced before the fix: the new `server/src/operator/cleanup.test.ts` failed for both commands.
   - `config.ts` exports `parseRetentionConfig(env)`: `IDEMPOTENCY_TTL_HOURS` min 1, `BLOB_ORPHAN_MIN_AGE_HOURS` and `BLOB_TMP_MAX_AGE_HOURS` min 0. `parseConfig` spreads it in place of its three inline rows. Both commands now call it, so an empty or non-integer value throws `ConfigError` (`missing:` or `invalid:<name>`). The existing catch prints the reason and exits 1. Nothing is deleted, because the throw comes before the connection or the blob store is opened.
   - `main` in both commands takes the environment as a defaulted parameter (`env: Env = readEnv()`) so the refusal can be tested in-process.
   - The `BLOB_TMP_MAX_AGE_HOURS` minimum stays 0, as the batch specified. Whether it should be 1 is a separate question for W0-04.
2. **queue-sla (resilience, low): one version without a frozen sla/calendar revision broke the whole queue and every daily digest.** `resolveFrozenConfiguration` now throws `NoConfigurationInForce` when `sla` or `calendar` is missing from `byKind`, so the submit refuses at write time. This fits D06's frozen clock. The old `viewRows.length === 0` guard is deleted: `sla` is itself a view kind, so that guard can no longer fire. The read side is unchanged. Every seed publishes both kinds (`server/src/configuration/seed.ts` `CONFIGURATION_SEED`, used by `fixtures:load` and the performance seed), and the submit integration tests stay green.

## What got smaller or clearer

- The two fallback defaults (`?? '72'`, `?? '1'`) are gone. The server and both operator commands now parse the retention thresholds through one path.
- One dead guard in `resolveFrozenConfiguration` is deleted.
- Production code: +22 / -12 lines across `config.ts`, `db-cleanup.ts`, `store-cleanup.ts` and `freeze.ts`. Tests: +53. Docs: the W0-02 section 5 variable table (`docs/engineering/implementation-plan-w1-w3.md`) now states the minimums and that an empty value is refused.

## Tests added

- `config.test.ts`: `IDEMPOTENCY_TTL_HOURS=''` gives `missing:IDEMPOTENCY_TTL_HOURS`.
- `operator/cleanup.test.ts`: `db:cleanup` with an empty TTL rejects with the `ConfigError` before it connects. The database URL points at a port with no Postgres, so any command that got past the parse would fail with a connection error instead. `store:cleanup` with an empty `BLOB_TMP_MAX_AGE_HOURS` rejects, and a fresh staging file is still present afterwards.
- `versions/freeze.test.ts`: the 'no view kind in force' case still throws. A new case with only `sla` missing also throws.
