# H28: Lane QC runs once per opening: no duplicate unavailable runs, no spurious 409 on approve

The final walkthrough re-verification on main `dfe84b3` found this. It still reproduced on `dfe84b3`: opening a submitted version as the AI/COE reviewer sent two `POST …/lanes/ai_coe/qc-run` requests. When the result was unavailable, each request recorded its own `qc_run` about 5 ms apart. The page could show the older run, and approving then failed with 409 `qc_run_superseded`.

## Finding addressed (medium), both halves

**(a) Why the page sent two requests.** It was not the effect dependencies, a remount or a second workspace. A probe on the real server showed that every effect on the page ran twice, `GET /api/session` included. The cause was the build. Vite follows the caller's `NODE_ENV`, and the browser suite (like any fixture-mode run) builds under `NODE_ENV=test`. That produced React's development bundle (776 kB, `jsxDEV` present), and under `<StrictMode>` it runs every effect twice. The fix is one line: `web/package.json` now builds with `NODE_ENV=production vite build`, so `npm run build` always produces the production bundle (519 kB, no `jsxDEV`), whatever the environment. The browser evidence now runs the same bundle as production. `web/vite.config.ts` says why in two lines. The two tests that pin the build script (`fixtures/src/substitutes/api/absence.test.ts`, `tests/integration/w1-int-substitute-absent.test.ts`) now pin the new string. They still refuse any substitute selection.

**(b) Why the server did not coalesce the two requests.** Only submit QC had the in-flight table. Lane QC (`approve_attempt`) had none. A completed run was protected anyway, because the second request's locked persist step replays a completed run. An unavailable run is retried by design (W0-07 3.7), so both requests inserted a row. `server/src/qc/orchestrator.ts` now runs both triggers through one `shareFlight` helper. It is keyed by case, version and lane (or `submit`), which is equivalent to W0-07's `runKey` for a frozen version. Concurrent calls share one run whatever it settles to, and the entry is removed when the call settles, as W0-07 3.4 step 2 describes. The run keeps the originating correlation. The 3.7 replay rules are unchanged, as are the late and ready checks and the 409 rule: a later, non-concurrent reopen after an unavailable run still records a new run.

**The UI approves with the run it shows.** No code change was needed. `LaneDecisionActions` already sends `state.run.runId`, the run the page displays. With one request per opening, and concurrent requests sharing one run, that run is the latest.

## Tests (fail before, pass after)

- `tests/integration/w2-05-dispositions.test.ts`, "lane QC coalesces concurrent calls for one version and lane into one unavailable run". It makes two concurrent `runAndPersistLaneQc` calls for (version, `ai_coe`) and one for `dpo`, with a runner that always answers unavailable. It expects the same outcome for the two `ai_coe` calls, one runner call per lane and one `qc_run` row per lane. It then checks that a settled unavailable run is retried. Before the fix it failed: the two `ai_coe` calls returned different run ids.
- `tests/browser/w2-int-07-reviewer-workspace.spec.ts`, "one opening runs lane QC once; approve names the unavailable run shown", on the real server. The owner sets slot 1 of RAI-2000-0004 to "not yet" and submits. The substitute's QC script then no longer matches, so the lane run is unavailable. AI/COE opens the version. The test expects exactly one `qc-run` response, the unavailable block shown, and the approve request carrying that run's id, followed by the "approval recorded" notice. Before the build fix, at 1440, it failed with `Expected length: 1, Received length: 2`.
