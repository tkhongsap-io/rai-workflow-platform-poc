# H18: One definition of 'latest disposition' and 'undispositioned'; no N+1 in the findings list

## Findings addressed

- **workflow-core simplify (medium): "'Latest disposition / undispositioned' defined five times, including an N+1 loop".** Still present on main `7617197`. "Latest disposition" was written out five times: `workflow/ready.ts` (the undispositioned ids, then a second LATERAL for the dispositioned count), `cases/status.ts` (the `awaiting_disposition` EXISTS that the queue, the case list and the case page share; the queue code named in the finding moved there with H3), `findings/repository.ts` `latestDisposition`, and the `listDispositions` ordering. `listFindingsForVersion` ran one `latestDisposition` query for every finding.

## Change

- `findings/repository.ts` exports the one definition. `latestDisposition` is a Drizzle subquery for each `qc_finding`'s latest `disposition_event`, joined `LATERAL ... ON true` and ordered `created_at DESC, id DESC`. Since H8, stamps are minted after the previous event under the case lock, so `created_at` is commit order and `id` only settles an equal stamp. `undispositioned` is the Ready rule's predicate: `(kind IS NULL OR kind = 'fixed_proposed')`.
- `workflow/ready.ts` runs one query for the version's findings, which returns each id with its `undispositioned` flag. The ids come from the flag. When Ready holds, no finding is open, so `dispositionedFindingCount` is the number of findings. The second LATERAL count query is deleted. Every kind other than `fixed_proposed` counts as dispositioned, so the count is the same as before.
- `cases/status.ts` builds its `awaiting_disposition` EXISTS from the same subquery and predicate.
- `listFindingsForVersion` is one joined query (`qc_finding` ⋈ `pack_version` ⟕ LATERAL latest disposition). `readLatestDisposition`, the renamed `latestDisposition` that the disposition service uses for the `fixed_confirmed` check and the stamp floor, joins the same subquery.
- `readFinding` and `listDispositions` had no callers and are deleted.
- One finding view: `qc/repository.ts` `storedFindingSummary(row)` maps a stored `qc_finding` to the shared `StoredFindingSummary` type, keeping only the string and number message params. `listFindingsForRun` and `listFindingsForVersion` use it. The orchestrator's `StoredFindingView` interface and the two `asMessageParams` copies are deleted. Both routes now return the findings without mapping them again.
- **Behaviour change:** the two `asMessageParams` copies handled an empty params object differently. The qc-run response, both fresh and replayed, kept `messageParams: {}`. `GET …/findings` dropped the field. `GET …/findings` now returns `{}` as well, so the same stored finding has the same shape in every response. The schema already allowed the field, and the SPA reads it as `finding.messageParams ?? {}`.

### Test that fails before and passes after

`w2-09-version-findings`, "lists every finding with its latest disposition (created_at DESC, id DESC) in one query". It adds a finding with empty params next to the qc-run findings. It inserts three dispositions on one finding: `waived` at t+1 with the largest id, then `not_applicable` and `fixed` at the same t+2. It then calls `listFindingsForVersion` through a Drizzle logger that counts queries, and asserts one query, `fixed` as the latest disposition (the later stamp beats the larger id, and the larger id wins an equal stamp), `null` for the finding with no disposition, and `messageParams: {}` from the GET. On main it failed with `one query regardless of finding count` (actual 4, expected 1). The w2-05, w2-06, w2-09 (existing test), w3-01 and queue repository tests are unchanged and pass.

## What got smaller

`server/src`: 87 lines added, 214 removed (net -127). Four hand-written LATERAL SQL blocks became one Drizzle subquery and one predicate. The N+1 loop, two dead exports, one duplicate interface, one duplicate helper and two per-field route mappings with their literal-union casts are gone. No new module was added.
