# H13: Notifications: true README, commit settled deliveries on shutdown, one outbox helper, dedupe composition checks, remove the production test hook

## Findings addressed

All seven findings still applied on main `7617197`.

- **Graceful shutdown rolls back a delivery the sink already accepted (low, bug).** On main, `deliverInitial` called `signal?.throwIfAborted()` after the sink call and again after the delivery update. An abort during a pending sink call therefore rolled back a mail the sink had already accepted, and the row stayed `queued` with `attempts = 0`. Fixed first, test first: the shutdown test now asserts `status = 'sent'` and `attempts = 1` after the sink is released, and that a later `deliverPending` with the aborted signal rejects with `AbortError` and sends nothing. Before the fix it failed with `AbortError`. In `service.ts`, a local `send` composes inside its own `try/catch` (a `CompositionError` or `DigestCompositionError` keeps its code; anything else is `sink_failure`), calls `signal?.throwIfAborted()` only before the sink, and wraps the sink call so the settled receipt is always committed. The two aborts after the sink are gone. Review wording changes from "rolls back after settlement" to "commits the settled result; no new row starts".
- **README.md and DIGEST.md are stale ticket handoff notes (medium).** They said there was no polling loop and that the initial runner never retries. Both are false now. They are replaced by one short `notifications/README.md` covering the outbox, the single-flight dispatcher (startup pass, 250 ms poll, post-response wakeup), the `SKIP LOCKED` attempt, 4 attempts with 1/5/25 s backoff, the digest producer and the shutdown drain. `DIGEST.md` is deleted. Ticket-ID header comments in `service.ts`, `compose.ts`, `digest.ts`, `retry.ts`, `runtime.ts`, `open-lanes.ts`, `ready-notice.ts` and `send-back-notice.ts` now give reasons. The `deliverInitial` doc now reads "Dispatches at most one eligible attempt for this row; a crash before commit can replay it." The stale `AppDeps.notifications` doc ("retries and digest remain separate") is corrected too.
- **Synthetic-address and base-URL/ID checks duplicated between compose.ts and digest.ts (low).** `compose.ts` exports `SAFE_ID` and `safeBaseUrl(base)`. `versionLink` uses both and still throws `CompositionError('unsafe_link')`. `digest.ts` drops its copy `synthetic` and imports `syntheticAddress`, `safeBaseUrl` and `SAFE_ID`. It keeps `requireValid(...)`, so digest failures keep their `DigestCompositionError` code. The mail sink's `validate.ts` loses the repeated `!realDay(event.digestDay) ||`, which the line above already returns on.
- **Outbox insert and case-version path builder written three times (low).** New `notifications/outbox.ts` exports `caseVersionPath` and `enqueueCaseNotifications(tx, {...})`. The helper inserts one row per recipient and leaves `status`, `attempts`, `next_attempt_at` and `last_error_code` to the database defaults. `open-lanes.ts`, `ready-notice.ts` and `send-back-notice.ts` call it. `laneOpenDeepLinkPath`, `readyDeepLinkPath` and `sendBackDeepLinkPath` are deleted, and w2-01 asserts against `caseVersionPath`. The dispatcher's row and composition equality check is unchanged.
- **workflow-core simplify (part): the production test hook.** `failAfterFirstLaneOpenNotification` and the `nodeEnv` plumbing that gated it are removed from `VersionServiceDeps`, `OpenLanesInput` and `app.ts`. w2-01 and w3-03a now force the rollback with a real database fault. One lane gets the same address twice, and the second insert violates `notification_event_version_lane_recipient_key` (23505; the index is in `server/drizzle/0004_w2_01_notification.sql`). Both tests still prove no partial rows: the draft stays open, there is no `lane.opened` or `version.submitted`, and there are no notification rows and no mail.
- **Ready integration test title claims "no retry runs" and its last assertion depends on wall-clock timing (low).** The test is renamed `Ready: owner only; failure=${fail} never undoes decisions and retry waits for its deadline`. The timing-dependent tail (the receipt count, a second `deliverPending` and the equality check) is replaced by `next_attempt_at IS NOT NULL`, selected in the existing query: true when failing, false otherwise.
- **The submit-latency test uses a sleep and a vacuous assertion (low, test gap).** Removed `started`, `await delay(100)`, `assert.ok(duration < performance.now() - started)`, the two re-checks after it and the now-unused `duration`. The `Promise.race` hang guard stays.
