# H27: UI: show send-back feedback on the sent-back version and on the owner's successor draft

The walkthrough re-verification on main `9103668` found this. It still applied on `b011139` (H26 merged): the version read served `decisions`, but no screen rendered them.

## Finding addressed

- **The owner could not see the reviewer's send-back feedback in the app, only in the mail (medium; A09).** This batch consumes H26's `SubmittedVersion.decisions`. No server or contract change.
  - The frozen version view lists its lane decisions: lane, decision, `Decided by {subject}`, and decided at. A send-back also shows each feedback item and the summary. The item is labelled by slot with the existing `review.send_back.slot_option` string ("Slot 2: Privacy checklist"), followed by the deficiency. The decision label reuses `projection.approved` / `projection.sent_back`. Reviewer identities render as the subject id, the same way the page shows `submittedBy`; there is no display-name lookup.
  - The successor draft shows "Feedback from version N" above the pack editor. It lists version N's send-backs, so the owner sees what to fix while editing. `loadAll` reads the parent version when the draft has a `parentVersionId`.
  - One component, `web/src/screens/case/lane-decisions.tsx`, serves both places. It renders a `section` labelled by its `h2` (a named region) with a list, and renders nothing when there is nothing to list. It sits in its own card, apart from the frozen pack, so the frozen card's text stays identical before and after a decision. The journey already asserts that.
  - Four new strings in both catalogues (Thai default): `pack.feedback_heading`, `version.decisions.heading`, `version.decisions.decided_by`, `version.feedback.summary`.
  - Doc updated: `implementation-plan-w1-w3.md` 7.6 (the case screen renders `decisions`) and the A09 browser column of the acceptance table.

## Test (fails before, passes after)

`tests/browser/w2-int-journey.spec.ts` (the W2-INT send-back/resubmit journey, real server) now follows the batch's scenario. The DPO sees its lane's QC result, then sends v1 back naming slot 2 with a deficiency and a summary. The spec used to have AI/COE send back slot 1. `expectSendBackFeedback` checks the named region, the DPO decision "sent back", the decider, exactly one feedback item with the slot 2 label and the deficiency, and the summary. It runs four times:

- for the DPO right after the decision;
- on v1 after the reload;
- for the owner on v1 (with an axe audit, `w2-int-journey-owner-v1-decisions-th`);
- for the owner on the v2 draft under "Feedback from version 1". The existing axe audit of the successor draft runs after the save.

With the catalogue keys and the spec change but before the UI change, the journey failed at the first check: no region named `version.decisions.heading`.

## What got smaller

Nothing got smaller. This is a UI consumer the app lacked. The additions are kept to one component used in two places, plus one parent read in `loadAll` and a short CSS block. They add no view-model function, no new route and no display-name lookup. Net `git diff --shortstat origin/main`: 8 files changed, 241 insertions(+), 34 deletions(-), including this record.
