# Intent: publish validation on the Admin paths and the implemented-rule registry (W6-03, #223)

W6-02 gave the store Admin drafts, publish and restore, checked only against each kind's schema. That is not enough for an Admin who edits configuration without a redeploy: a QC catalogue could name a rule the product does not implement (it would silently not run and read as a pass), move a rule to a trigger or engine it is not built for, give `v2.0` the v1.0 Sheet-3 band rule (L12), or leave a checklist template version without a catalogue entry (new submissions would reach `unknown_template_version`). A recipient list could name a real address while mail is only a sink.

This ticket adds one validator, `publishProblems(kind, body, inForce, mailMode)` in `server/src/configuration/validate.ts`, and the static registry it checks catalogues against, `IMPLEMENTED_RULES` in `@rai/shared`. The validator runs **only** in the Admin paths `publishDraft` and `restoreRevision`. `publishRevision` keeps exactly today's checks, so the seed, `fixtures:load` and the integration tests that publish a partial catalogue or a real recipient on purpose (`w4-02-rule-catalogue`, `w3-03b-digest`) are unchanged (W6 plan section 2.4, round 3).

It is order 3 on the Admin configuration stream of the [W6 plan](../../docs/engineering/implementation-plan-w6.md) (section 2.4, row W6-03), under the register rows "Ta's delegation (2026-09-27)" and "W6 delegated rulings (provisional)" (Q6: an unimplemented rule ID is refused on publish). No route (W6-04), no UI, no migration; `group_role_mapping` stays unregistered (W6-11). Synthetic data only; no network call; no deploy.
